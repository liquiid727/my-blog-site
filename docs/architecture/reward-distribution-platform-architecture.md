# 奖励发放中台架构：别让活动系统直接改用户资产

我以前看到“送用户 30 分钟体验时长”这种需求，第一反应很朴素：

不就是给某张表加一条记录吗？

后来奖励类型一多，事情就开始变得很有节目效果。

- 签到送积分
- 看广告送体验时长
- 活动送优惠券
- 新手任务送道具
- 充值返会员天数
- 故障补偿发限时权益

如果每个业务系统都自己判断、自己发、自己写流水、自己补偿、自己处理重复请求，那最后就会变成一种很熟悉的后端修仙场景：

**每个系统都觉得自己只是发一点小奖励，结果整个资产链路没人说得清。**

所以奖励发放这件事，不能只当成“运营小功能”看。它本质上是一个和用户资产、运营成本、财务核算、客服排障都相关的业务中台能力。

## 为什么必须统一发奖

奖励这件事最容易被低估，因为它看起来太碎了。

| 奖励类型 | 典型例子 |
| --- | --- |
| 时长 | 免费体验 30 分钟、活动送 2 小时、充值返 10 小时 |
| 道具 | 加速卡、排队优先券、房间皮肤、体验券 |
| 积分 | 签到积分、任务积分、兑换积分 |
| 权益 | VIP 体验、会员天数、限时特权 |
| 优惠 | 满减券、折扣券、充值券 |

它们表面上是不同资产，背后却有同一组问题：

- 这次发奖从哪里来？
- 发的到底是哪一个奖励包？
- 有没有重复发？
- 发了几份？
- 哪些项成功，哪些项失败？
- 后面客服、运营、财务能不能查到？
- 出问题后能不能重试、补发、对账？

如果没有统一入口，这些问题就会散落在签到系统、广告系统、任务系统、订单系统、活动系统和后台脚本里。

短期看是开发快，长期看就是资产口径不一致。

## 核心边界：业务系统只产生发奖请求

我更推荐的边界是：

**活动只产生“发奖请求”，不要直接改资产。**

签到、广告、任务、订单、活动、后台这些系统，只负责判断一件事：

**用户是否满足发奖条件。**

真正发什么、怎么发、发几份、是否重复、写什么流水、调用哪个资产服务、失败怎么处理，统一交给 Reward Service。

```text
签到 / 广告 / 任务 / 订单 / 活动 / 后台
                |
                | GrantRewardCommand
                v
          Reward Service
                |
    +-----------+-----------+-----------+
    |                       |           |
Reward Config        Reward Ledger   Idempotency
奖励包配置             发放流水        幂等控制
    |                       |
    +-----------+-----------+
                |
                v
          Asset Services
Time Wallet / Item Inventory / Points / Coupon / Membership / Privilege
```

这条边界定清楚之后，业务系统会轻很多。

它不用知道“加速卡具体怎么入库”，也不用关心“优惠券库存扣减失败怎么办”。它只要把一次明确的发奖请求交出来，并带上来源、业务号和请求号。

## Reward Service 该承担什么

一个最小可用的奖励中台，至少要拆出这几类能力：

```text
reward-service

RewardGrantService      // 发放服务
RewardPackageService    // 奖励包配置
RewardLedgerService     // 奖励流水
RewardRuleService       // 简单规则校验，后续可增强
RewardReconcileService  // 对账
```

它的定位不是“某个活动的发券工具”，而是所有运营奖励、系统补偿、任务奖励、活动奖励的统一发放入口。

换句话说，它要守住三件事：

1. **配置口径统一**：发什么，不散落在代码和脚本里。
2. **发放过程可追溯**：每一次发奖都有主记录和明细记录。
3. **资产变更可核对**：奖励流水和资产服务的真实入账结果能对得上。

## 发奖请求模型

所有来源都应该收敛成一个命令。

```go
type GrantRewardCommand struct {
    UserNo            string
    RewardPackageCode string

    SourceType string
    SourceNo   string

    BizNo     string
    RequestNo string

    OperatorType string
    OperatorNo   string

    Remark string
    Extra  map[string]any
}
```

这里面有几个字段很关键。

`RewardPackageCode` 表示发哪个奖励包。业务系统不应该自己拼奖励明细。

`SourceType` 和 `SourceNo` 表示来源，比如 `sign_in`、`ad_watch`、`campaign`、`order`、`manual_compensation`。这组字段是后续查询和对账的入口。

`BizNo` 是业务单号，比如活动参与记录、订单号、任务完成记录。

`RequestNo` 是请求号，适合承接上游调用幂等。如果上游能保证同一业务动作只有一个请求号，Reward Service 就能更稳定地识别重复请求。

`OperatorType` 和 `OperatorNo` 用来区分系统发放、运营后台发放、管理员补偿。这个字段平时看起来没什么存在感，但出问题时非常救命。

## 奖励包：不要把发什么写死在活动代码里

奖励包是这个中台的配置核心。

建议至少拆两张表：

- `reward_package`：奖励包主表
- `reward_package_item`：奖励包明细表

主表负责回答：

- 奖励包编码是什么
- 奖励包名称是什么
- 是否启用
- 有效期是什么
- 适用来源是什么
- 当前版本是什么

明细表负责回答：

- 奖励类型是什么
- 奖励资产编码是什么
- 数量是多少
- 有效期怎么计算
- 是否必须成功
- 发放参数是什么

例如一个“新手任务完成奖励包”可能包含：

| 类型 | 内容 | 数量 |
| --- | --- | --- |
| time | 体验时长 | 30 分钟 |
| points | 积分 | 100 |
| coupon | 满减券 | 1 张 |

业务系统只需要传 `new_user_task_complete_v1`，不要直接传“30 分钟 + 100 积分 + 1 张券”。

因为活动会变，运营会调，奖励会加版本。如果明细写死在业务代码里，每次改奖励都要发版，迟早会把人送进深夜上线。

## 发放主流程

一次同步发奖可以按下面的流程走：

1. 业务系统调用 `RewardGrantService.Grant()`
2. 校验 `reward_package` 是否存在、是否启用、是否在有效期内
3. 根据幂等键检查是否已经发过
4. 创建 `reward_grant_record`，状态为 `pending`
5. 展开奖励包明细，创建 `reward_grant_item`
6. 将主记录状态更新为 `processing`
7. 逐个调用资产服务发放
8. 记录每个奖励项的发放结果
9. 汇总更新主记录状态：`success`、`partial_failed` 或 `failed`
10. 返回发放结果

资产发放可以按类型分发：

```text
time   -> TimeWallet.AddEntry()
points -> PointsService.Increase()
item   -> ItemInventory.AddItem()
coupon -> CouponService.Issue()
member -> MembershipService.Grant()
right  -> PrivilegeService.Enable()
```

这里要注意一点：Reward Service 不一定要成为所有资产的数据库所有者。

更稳的做法是让它成为统一编排层。真正的资产落账仍然由各自 Asset Service 负责，这样资产领域本身的规则不会被奖励系统绕开。

## 幂等设计：发奖最怕“多发一次”

奖励发放的失败很麻烦，但重复发放更麻烦。

因为失败至少还能补，重复发放可能已经被用户消耗了。

常见幂等键可以这样设计：

```text
user_no + source_type + source_no + reward_package_code
```

如果同一个来源下允许多次发同一个奖励包，就要把业务动作粒度放进去：

```text
user_no + source_type + source_no + biz_no + reward_package_code
```

如果上游有稳定请求号，也可以额外记录：

```text
request_no
```

数据库层建议加唯一索引，不要只靠代码判断。

```sql
unique(user_no, source_type, source_no, biz_no, reward_package_code)
unique(request_no)
```

具体使用哪一个唯一键，要看业务语义。

比如每日签到，`biz_no` 可以是 `2026-05-15`。  
比如订单充值返利，`biz_no` 可以是订单号。  
比如一次后台补偿，`biz_no` 可以是补偿批次号 + 用户号。

幂等不是为了让接口“看起来优雅”，而是为了在超时、重试、消息重复、运营误点时，资产不会被打穿。

## 同步发还是异步发

不要把所有发奖都塞进一个模式。

小奖励适合同步发：

- 签到奖励
- 看广告奖励
- 评论奖励
- 新手任务奖励

这些奖励的用户体验要求是“立刻到账”。用户刚完成任务，如果奖励晚几分钟才出现，会觉得系统不可信。

大批量奖励适合异步发：

- 节日活动给 10 万用户发券
- 故障补偿给全量用户发 2 小时
- 排行榜结算
- 邀请活动批量结算

这类场景不要在同步接口里硬发。

更合理的链路是：

```text
reward_campaign_job
        |
        v
批量生成 GrantRewardCommand
        |
        v
进入队列
        |
        v
worker 分批发放
        |
        v
记录进度、失败、重试和汇总结果
```

也就是说，Reward Service 的 `Grant()` 能支持同步调用，但中台本身还需要 `Campaign Job + Queue + Worker` 承接批量任务。

## 流水表：不要只记录“成功了”

奖励流水建议分主表和明细表。

主表 `reward_grant_record` 记录一次发奖请求：

| 字段 | 含义 |
| --- | --- |
| grant_no | 发放单号 |
| user_no | 用户 |
| reward_package_code | 奖励包 |
| source_type/source_no | 来源 |
| biz_no/request_no | 业务号和请求号 |
| status | 主状态 |
| operator_type/operator_no | 操作方 |
| remark/extra | 备注和扩展信息 |

明细表 `reward_grant_item` 记录每一个奖励项：

| 字段 | 含义 |
| --- | --- |
| grant_no | 发放单号 |
| item_no | 明细单号 |
| reward_type | 奖励类型 |
| asset_code | 资产编码 |
| amount | 数量 |
| status | 明细状态 |
| asset_tx_no | 资产服务返回的交易号 |
| fail_code/fail_reason | 失败原因 |

主记录让你知道“这次发奖整体怎么样”。  
明细记录让你知道“具体哪一项出问题”。

这两层不能省。否则一个奖励包里有三项，其中两项成功、一项失败时，你只能得到一句很尴尬的“发奖失败”。

## 状态机和重试

推荐状态至少包括：

```text
pending
processing
success
failed
partial_failed
retrying
canceled
```

发奖失败的原因可能很多：

- 积分服务异常
- 时长钱包写入失败
- 优惠券库存不足
- 数据库超时
- 上游配置错误
- 资产服务返回幂等冲突

不要简单吞掉。

失败后要区分两类情况：

**可重试失败**，比如网络超时、服务临时不可用、数据库死锁。  
**不可重试失败**，比如奖励包配置错误、优惠券库存永久不足、资产编码不存在。

重试时也不要重新生成一套新流水，而是基于原 `grant_no` 或原 `grant_item` 做状态推进，避免把一次业务发奖拆成多笔真假难辨的记录。

## 对账能力

生产级奖励系统一定要能对账。

至少要支持这些查询：

- 按用户查奖励发放记录
- 按 `source_type/source_no` 查发放结果
- 按 `reward_package_code` 统计发放量
- 按 `reward_type` 统计发放资产
- 按活动批次查发奖总量
- 按失败状态查异常记录
- 按资产服务交易号反查发奖来源

对账本质上是在回答：

**Reward Service 认为自己发了什么，资产服务实际入了什么，这两边能不能对上。**

如果对不上，就要能定位：

- 是 Reward Service 记录成功但资产没到账？
- 是资产到账了但 Reward Service 没更新状态？
- 是重复请求被挡住了但上游误以为失败？
- 是某个批次只发了一半？

没有对账能力的奖励系统，就像一个没有账本的钱包。平时看不出来，出事只能靠人肉翻日志。

## 后台运营能力

奖励中台后续一定会长出后台。

至少需要这些功能：

- 奖励包列表
- 创建奖励包
- 编辑奖励包
- 启用 / 禁用奖励包
- 查看奖励包版本
- 查看发放记录
- 查看发放明细
- 手动补发奖励
- 重试失败发放
- 撤销奖励，谨慎开放
- 批量发放，谨慎开放
- 导出发放记录

其中“撤销奖励”和“批量发放”要特别谨慎。

它们不是普通按钮，而是会真实影响用户资产的运营能力。最好有权限控制、审批流、操作日志、二次确认和批次级审计。

## 最小落地版本

如果一开始不想做太重，可以先落一个最小版本：

1. 奖励包主表和明细表
2. 统一 `GrantRewardCommand`
3. 发放主记录和明细记录
4. 基于唯一索引的幂等控制
5. 同步发放链路
6. 失败状态和人工重试入口
7. 按用户、来源、奖励包的基础查询

先把“统一入口、统一流水、不重复、能查到”做好。

等业务增长后，再补：

- 批量发放任务
- 队列 worker
- 自动重试
- 对账任务
- 运营后台
- 配置版本管理
- 更复杂的规则引擎

不要一上来就做成巨型平台，但也不要让每个活动自己改用户资产。

这中间有一条很清晰的线：

**活动系统负责判断资格，Reward Service 负责完成发奖。**

## 结尾

奖励发放中台的目标，其实可以压成一句话：

**所有奖励统一入口、统一流水、可查、可重试、不重复。**

这不是架构洁癖，而是业务系统长大之后必须补上的账本。

小系统可以靠几段代码把奖励发出去。  
但只要奖励开始变成运营增长、用户补偿、会员权益和财务成本的一部分，就不能再让它散落在各个业务角落里自由生长了。

不然某天客服问“这个用户为什么多了 10 小时”，运营问“这个活动到底发了多少券”，财务问“这批补偿成本怎么算”，你就会发现：

最可怕的不是奖励没发出去。

而是发出去了，但没人知道它为什么发、从哪里发、发了几次。
